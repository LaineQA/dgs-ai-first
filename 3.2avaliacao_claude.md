Aqui está a análise crítica dos três testes:

---

## Teste 1 — Assertions vagas

```typescript
expect(res.status).toBe(200);
expect(res.body).toBeDefined();
```

**O que testa:** Apenas que o endpoint responde sem crashar e retorna *algum* body.

**O que falha em testar:**
- Não verifica a *forma* da resposta — `res.body` pode ser `{}` ou `{ error: "oops" }` e o teste passa.
- Não verifica que a resposta contém os campos esperados pelo domínio: resposta gerada, fonte/chunk, `queryId` para correlacionar com feedback.
- Não exercita que o pipeline RAG (busca → completion → response-builder) foi realmente executado.

**Risco se passar com código errado:** O endpoint pode retornar uma resposta vazia, truncada, sem fonte, ou até um objeto de erro com status 200 — e o teste dará verde. Em produção, usuários receberiam respostas sem sentido do assistente NovaTech.

---

## Teste 2 — Dados irreais (não exercitam o domínio)

```typescript
it('should handle empty question', async () => {
  expect(res.status).toBe(400);
});
```

**O que testa:** Um edge case válido em si, mas que *não precisa* de teste de integração — é puramente responsabilidade do `validator.ts` (Zod). Um teste unitário isolado seria suficiente e mais barato.

**O que falha em testar:**
- Não testa perguntas reais do domínio NovaTech ("prazo de devolução", "política de troca") contra o corpus em `data/retrieval-corpus/`.
- Não valida que a busca retorna chunks relevantes nem que a completion os usa corretamente.
- O projeto tem `tests/fixtures/queries.ts` exatamente para isso — fixtures de perguntas reais que deveriam estar sendo usadas aqui.

**Risco se passar com código errado:** A validação de input pode estar funcionando mas a lógica de busca e resposta pode estar completamente quebrada — nenhum teste de integração cobrirá isso. Cobertura de teste ilusória.

---

## Teste 3 — Mock que mascara bug

```typescript
const mockCreate = jest.fn().mockResolvedValue({ id: '123' });
// ...
expect(mockCreate).toHaveBeenCalled();
```

**Dois problemas críticos:**

**1. Usa `jest.fn()` em projeto Vitest.** O projeto usa Vitest (ver `vitest.config.ts` no Anexo C). O correto seria `vi.fn()`. Dependendo da configuração, `jest` pode não estar disponível — o teste pode falhar por razão errada, ou passar por acidente se o ambiente expor compatibilidade parcial.

**2. O mock nunca é conectado ao app.** `mockCreate` é criado mas não há nenhum `vi.spyOn` nem injeção de dependência que substitua o `prisma.feedback.create` (ou equivalente) real pelo mock. O teste faz uma requisição real ao endpoint, o endpoint usa a implementação real do banco, e então verifica se um mock que nunca foi chamado... foi chamado. O `expect(mockCreate).toHaveBeenCalled()` **sempre falhará** — ou pior, se o código crashar antes com status 500, o teste falha por razão diferente da verificada.

**Risco se passar com código errado:** Se alguém "consertar" o teste conectando o mock incorretamente (sem interceptar o módulo real), o feedback pode não ser salvo em produção e nenhum teste vai capturar isso.

---

## Resumo dos problemas por categoria

| # | Problema principal | Consequência |

| 1 | Assertions insuficientes | Bug na estrutura da resposta passa invisível |
