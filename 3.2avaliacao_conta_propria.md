## Revisão dos testes gerados por IA

### Teste 1 — `query endpoint` (assertions vagas)

- O que testa:
  - Que o endpoint `POST /api/query` retorna `200`
  - Que `res.body` está definido

- O que falha em testar:
  - Conteúdo da resposta (`answer`, `source_document`, `confidence_score`)
  - Se a resposta é correta para a pergunta de domínio sobre prazo de devolução
  - Se o corpo segue o formato esperado ou se contém dados úteis
  - Se a resposta contém a fonte correta e não é apenas um payload vazio

- Risco se passar mas o código estiver errado:
  - Falso positivo: o endpoint pode retornar `{}` ou um corpo inválido e ainda passar
  - Uma regressão no modelo ou no parser de resposta não seria detectada
  - A validação de domínio e structured output continua sem cobertura

---

### Teste 2 — `query endpoint edge cases` (dados irreais)

- O que testa:
  - Que `POST /api/query` com `question: ''` responde `400`

- O que falha em testar:
  - Comportamento em perguntas reais de logística ou business
  - Se o endpoint responde corretamente para perguntas válidas
  - Se o erro `400` tem mensagem ou motivo adequado
  - Se o domínio de perguntas está realmente coberto

- Risco se passar mas o código estiver errado:
  - O endpoint pode estar inválido para casos reais do produto e ainda passar
  - A validação de input vazio pode estar correta enquanto a lógica de busca/QA está quebrada
  - Não protege contra erros de conteúdo ou falta de fontes

---

### Teste 3 — `feedback endpoint` (mock que mascara bug)

- O que testa:
  - Que `POST /api/feedback` retorna `200`
  - Que `mockCreate` foi chamado

- O que falha em testar:
  - Integração real com persistência de feedback
  - Se o mock foi de fato injetado no código do endpoint
  - Se o payload enviado é validado corretamente
  - Se campos obrigatórios existem e se dados sensíveis são tratados corretamente
  - Se o projeto está usando `Vitest` em vez de `jest`

- Risco se passar mas o código estiver errado:
  - O teste pode ser inútil se `mockCreate` não estiver acoplado ao handler
  - Pode esconder que o feedback não está sendo salvo ou que o handler nunca chega ao create
  - Pode passar mesmo com bugs de validação, entrada ou armazenamento
  - Usa `jest.fn()` em um projeto que declara `Vitest`, indicando inconsistência de framework

---

## Conclusão

- `Teste 1` é insuficiente: valida apenas que há resposta, não que seja correta.
- `Teste 2` cobre um caso de input inválido, mas não o domínio real de perguntas.
- `Teste 3` é perigoso: o mock pode mascarar bugs e ainda não segue o framework correto.

Uma versão melhor do `Teste 1` deveria verificar o conteúdo esperado da resposta, por exemplo:
- `res.body.answer` contém prazo de devolução
- `res.body.source_document` está presente e é um documento válido
- `res.body.confidence_score` existe e está dentro de um intervalo esperado
